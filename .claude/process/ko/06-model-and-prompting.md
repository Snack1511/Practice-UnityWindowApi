# 모델 선택과 프롬프팅

## 1. 모델 선택 규약

슬래시 커맨드로 모델을 골라 작업을 실행한다. **커맨드를 안 쓰면 기본 모델**이다.

| 모델 | 쓰는 곳 |
|---|---|
| **기본** | 핵심 영역 — 실패가 비싼 곳. 구조 변경, 초기화 순서, 플랫폼 코드 |
| **최상위** | 기본 모델이 두 번 이상 실패한 문제. 아키텍처 전면 재설계. 한 턴이 수 분 걸리는 장기 자율 작업 |
| **저비용** | 오타, 주석, 문서 갱신, 기계적 리네임, 단일 함수 수정 |

### 올려야 하는 신호

실패가 **컴파일 에러가 아니라 런타임 조용한 실패**로 나타나는 영역. 저비용 모델로 시작하지 않는다.

- 코드 밖 등록 지점을 건드리는 작업 (설정 파일, 에디터 설정, 빌드 목록)
- 개발 환경에서 검증되지 않는 블록 (플랫폼 조건부 컴파일)
- 초기화·해제 순서에 얽힌 변경
- **세 파일 이상을 동시에 건드리는 변경**

### 내려야 하는 신호

- 수정 지점이 이미 특정됐고 한 파일 안에서 끝난다
- 문서만 고친다
- 실패해도 컴파일 에러로 즉시 드러난다

### 작업 시작 전에 대조한다

새 작업을 받으면 **첫 응답에서** 위 기준에 대조한다. 매 턴 하지 않는다 — 작업이 바뀔 때만.

**양쪽 다 멈추고 확인받는다.** 작업을 시작하지 않은 상태에서 묻는다 — 진행한 뒤에 알리면 이미 비싼 모델이 다 읽은 뒤다.

- **과한 모델을 쓰는 중** → **전환을 요청하고 대기한다.**
  한 번 왕복하는 비용이 비싼 모델로 전체 작업을 돌리는 비용보다 싸다. "그대로"라고 답하면 현재 모델로 진행.
  > 이 작업은 문서 갱신만 합니다. `<저비용 커맨드> <작업 내용>` 권장(비용 <N>%).
  > 전환하시겠습니까? "그대로"라고 답하면 <현재 모델>로 진행합니다.

- **모자란 모델을 쓰는 중** → **멈추고 확인받는다.** 이 방향의 실패는 즉시 드러나지 않는다.
  > 이 작업은 <등록 지점 N곳>을 건드립니다. 누락 시 컴파일 에러 없이 런타임에 실패합니다.
  > `<상위 커맨드>` 권장 — 그래도 이대로 진행할까요?

- **두 번 이상 같은 방식으로 실패했을 때** → 세 번째 시도 전에 상위 모델을 제안한다. 같은 모델로 재시도하지 않는다.

제안은 **커맨드까지 적어서** 사용자가 바로 복사할 수 있게 한다.
**요청은 작업당 한 번만.** "그대로"라고 답했으면 그 작업이 끝날 때까지 다시 묻지 않는다.

### 서브에이전트로 대신 돌리지 않는다

다른 모델로 서브에이전트를 띄우면 이 대화의 맥락(인수인계, 검증 절차, 앞선 판단 근거)이 끊긴다.
맥락을 상속하는 방식은 모델 지정이 무시되고, 모델을 고를 수 있는 방식은 백지에서 시작한다.
**실패가 조용한 프로젝트에서는 맥락 단절이 그대로 리스크다. 모델 전환은 사용자가 슬래시 커맨드로 한다.**

### 슬래시 커맨드 정의

`~/.claude/commands/<이름>.md`:

```yaml
---
description: <모델명>로 작업 실행
model: <모델 ID>
argument-hint: [작업 내용]
---

$ARGUMENTS
```

`model:` frontmatter는 **그 턴만** 해당 모델로 실행한다. 다음 턴은 세션 기본값으로 돌아온다.
여러 턴을 유지하려면 `/model`로 세션 기본값을 바꾼다.

## 2. 프롬프팅 원칙

모든 모델에 적용된다. 모델별 문서를 따로 둔다면 **여기서 벗어나는 부분만** 적는다.

### 2-1. 금지가 아니라 이유를 준다

제약의 배경을 설명하면 모델이 일반화한다. 규칙만 나열하면 그 규칙 밖에서 어긋난다.

- ❌ `절대 <함수>를 직접 쓰지 마라`
- ✅ `<리소스 로드>는 <래퍼>를 거친다. 캐시와 참조 카운트가 여기에 있어서, 직접 호출하면 같은 자원이 중복 로드된다`

### 2-2. 하지 말 것보다 할 것을 적는다

- ❌ `장황하게 쓰지 마라` → ✅ `결론부터 한 문장. 근거는 그 뒤에`

### 2-3. 알아서 하길 바라면 그렇게 말한다

- ❌ `세이브 시스템 만들어줘`
- ✅ `세이브 시스템 만들어줘. 예외 처리, 마이그레이션, 손상 파일 복구까지 포함해서 실사용 가능한 수준으로`

### 2-4. 모르는 걸 모른다고 말할 여지를 준다

> 판단할 근거가 부족하면 추측하지 말고 부족하다고 말한다.

환각을 줄인다. 실패가 즉시 드러나지 않는 프로젝트에서 특히 중요하다.

### 2-5. 예시는 1개로 시작한다

형식·톤·구조를 맞추는 가장 확실한 수단. 출력이 여전히 안 맞을 때만 늘린다. 3~5개가 상한.
**피하고 싶은 패턴이 들어간 예시는 넣지 않는다** — 모델은 예시를 따라한다.

### 2-6. 지금은 덜 필요해진 것들

| 기법 | 현재 상태 |
|---|---|
| XML 태그 구조화 | 아주 복잡한 프롬프트에서만. 보통은 제목과 줄바꿈으로 충분 |
| 역할 부여 ("당신은 최고의 ~") | 대개 불필요. 과하게 규정하면 오히려 성능이 떨어진다 |
| "단계별로 생각해봐" | thinking이 대체. 최신 모델은 기본으로 켜져 있다 |
| 응답 프리필 | 최신 모델에서 API 오류 |

### 2-7. 첫 턴에 전체 명세를 준다

요구사항을 여러 턴에 걸쳐 흘리면 토큰 효율과 결과 품질이 같이 떨어진다.

```
목표: <끝났을 때 무엇이 되어 있어야 하는가>
산출물: <파일/코드/문서 — 구체적으로>
제약: <건드리면 안 되는 것, 성능·의존성 조건>
배경: <기존 코드의 어떤 문제 때문에 하는가>
```

채울 게 없는 항목은 빈칸으로 두지 말고 지운다.

### 2-8. 검증 못 한 것을 끝났다고 하지 않는다

세션 안에서 검증 불가능한 영역을 프로젝트마다 명시해둔다. 건드렸으면 "수정함"이 아니라
**"수정함, 단 X는 실제 빌드로 확인 필요"**라고 적는다.

### 2-9. 효과 수준(effort)은 프롬프트로 못 바꾼다

`effort`는 세션 설정(`/config`)이지 문서나 프롬프트로 올리는 값이 아니다.
"깊이 추론하세요" 같은 문장은 동작을 바꾸지 않는다. **추론이 얕으면 프롬프트를 고치지 말고 effort를 올린다.**

## 3. 도구 연결이 끊겼을 때

MCP 등 외부 도구 연결이 작업 도중 끊기면 **대체 수단으로 넘어가기 전에 재연결을 먼저 시도한다.**

- 재시도 정책: 최대 **5회**, 총 **1분** 예산
- 한계를 넘겨도 실패하면 **사용자에게 알리고 어떻게 진행할지 묻는다**

임의로 다른 접근으로 우회하면 결과가 달라지고 그 사실이 드러나지 않는다.
