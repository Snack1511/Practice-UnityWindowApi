# 세션 프로세스

작업 하나를 받아서 끝낼 때까지의 순서. **각 단계는 앞 단계가 끝나야 시작한다.**
단계별 상세는 링크된 문서에 있다.

```
0. 재개 확인  →  1. 접수  →  2. 범위 확정  →  3. 조사
                                                  ↓
9. 인수인계  ←  8. 기록  ←  7. 보고  ←  6. 검증  ←  4~5. 구현
```

---

## 0. 재개 — 세션이 끊겼다 이어질 때

**기억이 아니라 실제 상태를 먼저 읽는다.** 응답이 잘려도 이미 실행된 부작용은 되돌아가지 않는다.
가장 위험한 행동은 "안 됐겠지" 하고 다시 실행하는 것이다.

```bash
git status --porcelain      # 작업 트리에 무엇이 남아 있나
git log --oneline -3        # 커밋이 실제로 됐나
git status -sb | head -1    # 푸시됐나 (ahead/behind)
```

파일을 고치던 중이었다면 **그 파일을 읽어 의도한 내용이 이미 들어갔는지 확인**한 뒤 재수정한다.

| 행동 | 재실행 | 재개 시 |
|---|---|---|
| 파일 읽기 · grep · diff | 안전 | 그냥 다시 한다 |
| 파일 쓰기 · Edit | **주의** | 먼저 읽어서 이미 반영됐는지 확인 |
| `git commit` | **위험** | `git log` 확인. 했으면 amend, 안 했으면 commit |
| `git push` | **위험** | `git status -sb`의 ahead 수 확인 |
| 서브에이전트 | **위험** | 백그라운드에서 계속 돈다. 다시 띄우지 말고 알림을 기다린다 |

무엇이 끝났고 무엇이 안 끝났는지 **먼저 보고한 뒤** 이어간다. 끊긴 사실을 감추고 조용히 재시도하지 않는다.
**잘린 응답에서 받은 승인은 승인이 아니다.** 다시 확인받는다.

`HandOff.md`가 있으면 함께 읽고, 문서 기준과 실제가 다르면 그 차이를 먼저 보고한다.

## 1. 접수 — 무엇을 요청받았나

### 1-1. 질문인가 지시인가

| 형태 | 예 | 행동 |
|---|---|---|
| 질문 | "~할 수 있나?", "~방법 없나?", "이거 왜 이래?" | **대답만.** 파일을 고치거나 만들지 않는다 |
| 지시 | "~해라", "~하자", "진행해", "추가해" | 실행한다 |
| 애매 | "이거 고치는 게 낫지 않나?" | 대답하고 **"할까?"로 끝낸다** |

**조사는 추가 작업이 아니다.** 정확히 답하려고 파일을 읽고 `grep` 하고 로그를 뒤지는 것은 대답의 일부다.
경계는 **읽기와 쓰기**다 — 읽는 건 얼마든지, 쓰는 건 지시받았을 때만.

질문에 답하다가 코드를 써야 답이 되겠다 싶으면, 코드 대신 방법을 적고 **"써줄까?"**라고 묻는다.

### 1-2. 모델이 맞나

작업을 위 기준에 대조한다. 안 맞으면 **작업을 시작하지 않은 상태에서** 전환을 요청하고 대기한다.
매 턴 하지 않는다 — 작업이 바뀔 때만. → [06-model-and-prompting.md](06-model-and-prompting.md)

### 1-3. 지시가 모호하면 묻고 대기한다

- 해석에 따라 **결과물이 크게 달라지는** 모호함
- 필수 맥락 누락: 대상 파일 불명, 기존 코드 어디에 붙는지 불명, 성공 조건 불명

이 기준을 넘지 않으면 묻지 않는다. 변수명·기본값·동등한 두 방식 중 선택은 합리적인 쪽을 고르고 한 줄로 알린다.
질문은 한 번에 모아서 하고, 추측으로 채운 부분도 함께 밝힌다.

## 2. 범위 확정 — 어디까지 건드리나

**티켓(작업 단위) 스코프를 지킨다.** → [02-git.md](02-git.md) §1

1. `git status`로 **기존 변경을 확인한다.** 다른 세션/작업의 변경이 이미 올라와 있을 수 있다.
2. 내 수정과 남의 수정이 한 파일에 섞이면 **그 사실을 명시적으로 보고한다.**
3. 요청 범위 밖의 코드는 개선 여지가 보여도 수정하지 않는다. 발견한 문제는 **보고만** 남긴다.

**초기화·정리 작업은 추가와 정돈만 한다.** 삭제는 명시적으로 요청받았을 때만.

---

## 3. 조사 — 코드보다 문서가 먼저

1. 프로젝트 문서(`docs/`, `advise/`, 명세서)를 먼저 본다. 코드를 새로 훑는 것보다 빠르다.
2. **확정된 정책 결정을 버그로 오인하지 않는다.** "왜 이렇게 안 했지?" 싶은 지점이 의도적 결정일 수 있다.
   메모리·명세서에서 먼저 확인한다. → [05-memory.md](05-memory.md)
3. 그다음 코드를 읽는다.

---

## 4. 구현 전 — 이미 있는 것부터 찾는다

**코드를 추가하기 전에 같은 동작을 하는 코드가 이미 있는지 확인한다.**
있으면 **사용자에게 방향을 묻는다** — 새 메서드를 추가할지, 기존 것을 재사용할지.

이 확인 없이 유사 코드를 새로 만드는 것이 가장 흔한 낭비다.

## 6. 검증 — 고쳤다고 말하고 끝내지 않는다

각 단계를 **실제로 했는지 밝힌다.**

| # | 단계 | 언제 |
|---|---|---|
| 1 | `git diff` 정적 검토 | **항상.** 의도한 파일만 바뀌었는지, 부수 변경이 없는지 |
| 2 | 컴파일 · 정적 검사 | 코드를 고쳤으면 항상. **이 단계가 못 보는 범위를 명시한다** |
| 3 | 실제 대상 빌드 | 2단계가 컴파일하지 않는 코드(플랫폼 조건부 블록 등)를 건드렸을 때 |
| 4 | 실행 확인 | 사람이 봐야 판정되는 것. **무엇을 눈으로 볼지 목록으로 제시** |
| 5 | 세션 안에서 변경 내용 제시 | 파일별 diff와 각 변경의 이유. **Artifact는 요청받았을 때만** |

### 지키는 원칙

**하지 않은 검증을 했다고 하지 않는다.** 1단계만 했으면 "정적 검토만 했고 컴파일은 확인 못 했다"라고 적는다.
실패가 런타임에야 드러나는 프로젝트에서는 **근거 없는 완료 보고가 가장 비싼 실수다.**

## 7. 보고

- 결론부터. 근거는 그 뒤에.
- **안 한 것을 먼저 밝힌다** — 미검증 항목, 범위 밖이라 손대지 않은 것, 추측으로 채운 것.
- 범위 밖에서 발견한 문제는 수정 대신 여기에 적는다.

## 8. 기록

### 커밋

티켓 단위로 나눠 올린다. **커밋 트레일러를 넣지 않는다.** push는 명시 요청이 있을 때만.
→ [02-git.md](02-git.md)

### 문서

- 명세서·조사 문서는 **레포 안에 md로.** Artifact 발행 금지.
- 새 문서는 같은 폴더의 기존 문서 형식(파일명·헤더 구조)을 따른다.
- 새 문서는 **untracked로 남겨두고** 커밋 여부는 사용자 판단에 맡긴다.
- Change log에는 변경 내용뿐 아니라 **사용자 설명 뒤에 있는 의도(목표)**를 함께 적는다.

→ [03-docs.md](03-docs.md), [04-templates.md](04-templates.md)

### 메모리

작업 방식에 대한 지시를 받았으면 저장한다. 레포가 이미 기록하는 것은 저장하지 않는다.
→ [05-memory.md](05-memory.md)
