# 문서 체계

문서는 **두 축**이다. 성격이 달라서 합치면 둘 다 못 쓴다.

| 축 | 폴더 | 무엇을 담나 | 수명 |
|---|---|---|---|
| **코드베이스 문서** | `docs/` · `advise/` | 이 코드가 지금 어떻게 동작하는가 / 어떻게 바꿔야 하는가 | 코드와 함께 계속 갱신 |
| **작업 명세 문서** | `WorkFlow/<기능>/` | 이 작업을 언제 왜 어떻게 했는가 | 작업 시점에 쓰고 이후 참조만 |

`docs/architecture.md`는 "지금 구조"고, `WorkFlow/.../작업내역_*.md`는 "그날 무엇을 했나"다. 서로 대체하지 않는다.

## 공통 원칙

- **문서는 레포 안에 md로.** 명세서·조사 문서를 Artifact로 발행하지 않는다.
  팀이 레포 내 문서 폴더 규칙을 쓰고 있으면 아티팩트 링크는 그 흐름 밖에 있고 레포에 남지도 않는다.
- **새 문서는 같은 폴더의 기존 문서 형식**(파일명·헤더 구조)을 따른다. 쓰기 전에 먼저 확인한다.
- **새 문서는 untracked로 남겨두고** 커밋 여부는 사용자 판단에 맡긴다 (티켓 스코프 규칙과 같은 맥락).
- **정본(source of truth) 1곳 + 나머지는 델타만.** 같은 정보를 두 문서에 쓰지 않는다.
  여러 문서가 같은 내용을 다루면 어느 문서/커밋이 정본인지 각 문서 머리에 적는다.

## 1. 코드베이스 문서 — `docs/` · `advise/`

**`docs/` = 지금 어떻게 동작하는가. `advise/` = 어떻게 바꿔야 하는가.** 중복 서술하지 않는다.
제언이 반영되어 "현재 동작"이 되면 `docs/`로 옮기고 `advise/`에는 해결 표기만 남긴다.

### `docs/`

| 파일 | 내용 |
|---|---|
| `README.md` | 폴더 맵, 부트 시퀀스, **"어디를 봐야 하나" 표** |
| `architecture.md` | 초기화 순서, 계층 구조, 공용 패턴 |
| `CHANGELOG.md` | 시간순 변경 이력 |
| `<도메인>.md` | 도메인별 상세 |
| `reference/` | 외부 자료 분석. **적용 여부와 무관하게 보관** |

`reference/`는 제언이 아니라 **판단 근거**다. `advise/`의 10개 카운트에 포함하지 않는다.

`docs/README.md`의 핵심은 **"어디를 봐야 하나" 표**다. 작업 종류 → 문서를 직접 연결하면 매 세션 코드를 새로 훑지 않는다.

### `advise/`

- 파일명 `NNN-주제.md` — 3자리 일련번호, **재사용 금지**
- 각 항목은 **현상 → 근거(`파일:줄`) → 영향 → 권장** 순서
- **근거 없는 항목은 넣지 않는다**
- 해결된 항목은 지우지 말고 `~~취소선~~` + `✅ 해결 (커밋 해시)` — 판단 이력이 남는다
- `README.md`의 목록 표를 항상 함께 갱신한다

| 등급 | 뜻 |
|---|---|
| **P0** | 지금 빌드/실행이 안 됨 |
| **P1** | 동작은 하지만 조건에 따라 틀린 결과 |
| **P2** | 지금은 괜찮지만 규모가 커지면 비용이 급증 |

P0를 먼저 처리한다. 빌드가 안 되는 상태에서 리팩터링을 얹으면 원인 분리가 불가능해진다.

**10개 규칙** — 문서가 10개를 넘어가는 시점에 전체 재정리한다(카운트는 `README.md` 제외).
`README.md`에 현재 카운트(`N / 10`)를 적어두고 매번 갱신한다. 재정리 시:

- 해결 완료 문서는 `advise/archive/`로 이동 — 이력은 보존하되 목록에서 걷어낸다
- "레이어별"과 "우선순위별" 중 하나로 분류를 단일화한다
- 반영되어 "현재 동작"이 된 내용은 `docs/`로 승격
- 문서가 늘어도 진입점은 `README.md` 하나

### CHANGELOG 양식

시간순, 최신이 위. 항목 하나가 커밋 하나에 대응할 필요는 없다 — **하나의 판단 단위**로 묶는다.

```markdown
## YYYY-MM-DD — <무엇을 했나> (advise/NNN-N)

<왜 했나. 어떤 증상이 있었나.>

### 변경 범위
| 대상 | 변경 |

### 판단이 갈렸던 지점
**<선택 A를 했다.>** <다른 선택지가 왜 안 되는지.>

### 넣지 않은 것
<검토했지만 안 넣은 것과 이유. 다음 사람이 같은 검토를 반복하지 않는다.>

### 검증
| 단계 | 결과 |
| <육안 확인 항목> | ❌ 미확인 — <왜 못 했는지> |
```

**미확인 항목을 표에서 빼지 않는다.** 빼면 다음 사람이 확인된 걸로 읽는다.

## 2. 작업 명세 문서 — `WorkFlow/`

기능(컨텐츠) 단위로 폴더를 만들고 그 아래 성격별로 나눈다.

```
WorkFlow/
└── <기능명>/
    ├── 명세서/                        # 정본: 구현 명세서, 이관 명세서
    │   ├── <기능>_구현명세서.md
    │   ├── 시스템/시스템N_<주제>.md    # 대형 기능은 시스템별 분할
    │   └── 서브/서브N_<주제>.md
    ├── YYYY-MM-DD/                    # 날짜별 작업 내역 (세션 단위)
    │   ├── 작업내역_<기능>_<주제요약>.md
    │   └── 남은작업_<기능>_순차.md
    └── Change_log/
        └── <프로젝트>/YYYY-MM-DD_<주제>_Change_log.md
```

문서 템플릿 6종은 [04-templates.md](04-templates.md).

### 공통 헤더

문서 첫머리에 blockquote로 메타 정보. 항목은 문서 유형에 따라 취사선택.

```markdown
# <기능명> — <문서 성격> (<날짜 또는 부제>)

> 작성: YYYY-MM-DD / 작업자: <이름> (또는 세션/워크트리명)
> 브랜치: <작업 브랜치> / 기준: <기준 커밋 SHA 또는 시점>
> 소스: <이식·참조 원본 브랜치 tip SHA>      ← 이관/포팅 문서일 때
> 기획: <기획서 링크>
> 선행: <선행 커밋/문서>                      ← 의존 관계가 있을 때
> 성격: <문서의 역할 한 줄>
```

### 표기 규약

- **상태 이모지**: ✅ 완료 · ⚠️ 부분/주의 · ❌ 실패/미착수. 표의 상태 열에 사용
- **함정 마킹**: 반복적으로 실수가 나는 규약·제약은 섹션 제목에 `★함정`
- **해소된 항목은 지우지 않고** `~~취소선~~` + `(해소, 날짜)`
- **경고**는 ⚠️ 접두로 인라인
- **결함/이슈는 번호 붙은 표**로: `| # | 파일 | 결함 | 수정 |` — 후속 문서에서 `§2-2 #15` 식으로 참조 가능
- 코드 심볼·경로·SHA는 백틱

### Change log

- 저장 위치는 프로젝트 규칙을 따른다 (예: `C:\Git\Change_log\{ProjectName}\`).
- **변경 내용뿐 아니라 사용자 설명 뒤에 있는 의도(목표)를 함께 적는다.** 무엇을 바꿨는지만으로는 나중에 판단 근거가 안 남는다.

### 정책 결정 기록

기획/담당자가 확정한 정책 결정을 기록할 때는 다음을 **함께** 넣는다.

- 결정 내용 (무엇을 하기로 / 하지 않기로 했는지)
- **의도적 제외 범위** — 왜 뺐는지, 어떤 경로/유저가 영향받는지
- 제외의 한계 — 후속 리포트가 오면 이 결정이 원인인지 대조할 수 있도록

**확정된 정책 결정을 버그로 오인하지 않는다.** "왜 이렇게 안 했지?" 싶은 지점이 의도적 결정일 수 있다.

## 3. `HandOff.md` — 인수인계

세션이 끊긴 뒤 이어받기 위한 문서. 프로젝트 루트에 둔다.

**코드를 읽으면 아는 것은 적지 않는다.** 코드에 안 남는 것만 적는다 —
왜 그렇게 했는지, 무엇을 시도했다 접었는지, 무엇이 아직 확인 안 됐는지.

```markdown
# HandOff

마지막 갱신: <YYYY-MM-DD> / <원격 동기화 상태>

## 지금 상태
**작업 트리 <클린/변경 있음>, 미푸시 커밋 <N>개, 실행 중인 프로세스 <있음/없음>.**

### 도달한 지점
| 항목 | 상태 |          # ✅ 해결 + 어떻게 검증했는지 / ⚠️ 코드 완료, 검증 미완

## 다음에 할 일
**먼저 볼 것** — <대개 지난 세션이 못 끝낸 검증>
### 열린 항목
| 항목 | 문서 | 비고 |   # 왜 아직 안 했는지, 무엇을 알아야 손댈 수 있는지

## 재개에 필요한 환경 정보
### 도구 버전        # 요구 버전 + 실제 설치 경로 + 다른 버전으로 열면 안 되는 이유
### 빌드 · 검사      # 명령 + 출력 경로 주의사항 + 임시 스크립트 정리 규칙
### 실행 로그        # 경로 + 어떤 태그로 무엇을 판정하는지
### 디버그 조작      # 키/커맨드. 매핑이 코드 순서에 의존하면 그 사실도

## 이 프로젝트에서 반복해서 물린 함정
<실제로 물린 것만. 일반론은 적지 않는다.>
<"증상 X를 원인 Y로 봤는데 실제로는 Z였다" 형태의 오진 이력이 특히 값지다.>

## 재개 첫 동작
git status --porcelain / git log --oneline -3 / git status -sb | head -1
이 문서 기준과 다르면 그 차이를 먼저 보고한 뒤 진행한다.
```
