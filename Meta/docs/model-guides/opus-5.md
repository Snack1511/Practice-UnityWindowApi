# Opus 5 작업 규약

`/opus5` 또는 커맨드 없이 실행할 때. 공통 원칙은 [README](README.md), 모델 선택 기준은 [CLAUDE.md](../../../CLAUDE.md).

이 프로젝트의 **기본 모델**. Opus 4.8과 값이 같고($5/$25) 어려운 작업에서 더 강하다.
다중 파일 기능 추가, 대형 리팩터, 끝까지 완결하는 작업이 강점 — 스텁이나 자리표시자를 남기지 않는다.

문제는 능력이 아니라 **과잉**이다. 아래는 전부 그걸 깎는 규약이다.

## 지우면 좋아지는 지시

### 검증하라는 지시

Opus 5는 **시키지 않아도 스스로 검증한다.** "마지막에 검증 단계를 넣어라", "서브에이전트로 교차 검증해라" 같은 지시는 과잉 검증을 유발한다. **지우면 품질 손실 없이 토큰만 준다.**

"한 번 더 확인해줘", "다시 검토해봐" 같은 일상 표현도 같다. 일반적으로는 좋은 프롬프팅이지만 **이 모델에서는 역효과다.**

### 위임하라는 지시

Opus 4.8과 정반대. Opus 5는 서브에이전트를 알아서 잘 띄운다. 오히려 상한이 필요하다.

> 서브에이전트는 진짜로 독립적이고 규모 있는 작업에만 쓴다 — 여러 파일에 걸친 넓은 조사 같은 것. 도구 몇 번으로 끝낼 일은 직접 한다. 자기 작업을 검증하거나 재확인하는 용도로는 쓰지 않는다. 하나로 끝날 일에 여러 개 띄우지 않는다.

`Assets/Script/` 39개 파일이 전부인 프로젝트다. 대부분의 작업은 위임 오버헤드가 이득보다 크다.

### 길이를 effort로 줄이려는 시도

`effort`는 **생각하는 양**을 조절하지 **말하는 양**을 조절하지 않는다. 낮춰도 눈에 보이는 응답 길이는 안정적으로 안 줄어든다. 줄이려면 프롬프트로 지시한다.

> 답변은 간결하게. 주의사항과 단서는 짧게 하고 본론에 분량을 쓴다. 설명 요청에는 개요만 주고, 상세는 따로 요청받았을 때만.

## 넣으면 좋아지는 지시

### 1. 요청한 범위만

시키지 않은 단계를 덧붙이거나 작업 범위를 스스로 재해석하는 경향이 있다.

> 요청받은 것을, 요청받은 범위로 전달한다. 일상적 판단은 직접 내리고, 해석에 따라 결과물이 크게 달라지는 경우에만 확인한다. 접근이 잘못됐다고 판단되면 한 문장으로 말하고 요청대로 진행한다 — 조용히 범위를 좁히거나 넓히거나 바꾸지 않는다. 작업 전체를 끝내되, 요청 범위를 명백히 벗어나는 행동은 하지 않는다.

씬 하나 추가하랬더니 씬 시스템을 리팩터하고 있으면 [advise/002](../../advise/002-scene-system.md)와 충돌한다.

### 2. 서술 분량 조절

에이전트 작업 중 "이제 ~하겠습니다" 예고가 잦고, 메시지당 출력이 길다. 원하는 리듬을 직접 기술한다.

> 첫 도구 호출 전에 무엇을 할지 한 문장. 작업 중에는 중요한 걸 찾았거나 방향을 틀 때만 짧게. 끝나면 결과부터 — 첫 문장이 "무슨 일이 있었나"에 답하고, 근거는 그 뒤에.

### 3. 파일 산출물 길이

대화 응답과 **별개로**, 디스크에 쓰는 문서(리포트, 마크다운, 요약)가 길어진다. `docs/`나 `advise/` 갱신 시 명시한다.

> 문서 길이는 내용에 맞춘다. 채워넣기용 섹션, 중복 요약, 상투적 서두를 넣지 않는다.

### 4. 자기 수정 서술 억제

앞서 한 말을 정정할 때 장황해진다.

> 사용자의 코드·결론·판단이 바뀌는 오류만 정정한다. 짧게 말하고 작업을 계속한다. 사용자에게 아무 영향 없는 실수는 조용히 고치고 넘어간다.

### 5. 코드 리뷰는 "전부 보고 → 나중에 거르기"

"심각한 것만", "보수적으로" 같은 지시를 **문자 그대로 따른다.** 버그를 찾아놓고 기준 미달이라 판단해서 보고를 생략한다. 정확도는 오르지만 재현율이 떨어져 보인다.

> 확신이 없거나 사소하다고 판단되는 것도 전부 보고한다. 이 단계에서 중요도로 거르지 않는다. 각 항목에 확신도와 심각도를 붙인다.

## 참고

- **thinking이 기본으로 켜져 있다.** Opus 4.8과 다르다.
- **`low`·`medium`이 유난히 강하다.** 이전 모델 기본값을 그대로 옮기면 대개 과하다. 기본은 `high`, 어려운 코딩·에이전트 작업만 `xhigh`.
- **비전 작업은 도구를 준다.** 이미지를 자르고 확인할 도구가 있을 때가, thinking을 올리는 것보다 싸고 효과적이다.
