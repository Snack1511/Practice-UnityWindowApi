## 공통 원칙

모든 모델에 적용된다. 개별 문서는 **여기서 벗어나는 부분만** 적는다.

### 1. 금지가 아니라 이유를 준다

제약의 배경을 설명하면 모델이 일반화한다. 규칙만 나열하면 그 규칙 밖에서 어긋난다.

- ❌ `절대 Resources.Load를 직접 쓰지 마라`
- ✅ `에셋 로드는 ResourcesManager를 거친다. 캐시와 참조 카운트가 여기에 있어서, 직접 호출하면 같은 에셋이 중복 로드된다`

### 2. 하지 말 것보다 할 것을 적는다

- ❌ `장황하게 쓰지 마라`
- ✅ `결론부터 한 문장. 근거는 그 뒤에`

### 3. 알아서 하길 바라면 그렇게 말한다

모호한 지시로 "알아서 잘"을 기대하지 않는다. 기본 이상을 원하면 명시적으로 요구한다.

- ❌ `세이브 시스템 만들어줘`
- ✅ `세이브 시스템 만들어줘. 예외 처리, 마이그레이션, 손상 파일 복구까지 포함해서 실사용 가능한 수준으로`

### 4. 모르는 걸 모른다고 말할 여지를 준다

> 판단할 근거가 부족하면 추측하지 말고 부족하다고 말한다.

환각을 줄인다. 이 프로젝트는 실패가 런타임에야 드러나므로 특히 중요하다.

### 5. 예시는 1개로 시작한다

형식·톤·구조를 맞추는 가장 확실한 수단. 출력이 여전히 안 맞을 때만 늘린다. 3~5개가 상한이다.
피하고 싶은 패턴이 들어간 예시는 넣지 않는다 — 모델은 예시를 따라한다.

### 6. 지금은 덜 필요해진 것들

최신 모델에서는 효과가 줄었다. 습관적으로 넣지 않는다.

| 기법 | 현재 상태 |
|---|---|
| XML 태그 구조화 | 아주 복잡한 프롬프트에서만. 보통은 제목과 줄바꿈으로 충분 |
| 역할 부여 ("당신은 최고의 ~") | 대개 불필요. 과하게 규정하면 오히려 성능이 떨어진다 |
| "단계별로 생각해봐" | thinking이 대체. Opus 5·Sonnet 5·Fable 5는 기본으로 켜져 있다 |
| 응답 프리필 | Opus 4.6 이후 전 모델에서 API 오류 |

### 7. 첫 턴에 전체 명세를 준다

전 모델 공통. 요구사항을 여러 턴에 걸쳐 흘리면 토큰 효율과 결과 품질이 같이 떨어진다.

```
목표: <끝났을 때 무엇이 되어 있어야 하는가>
산출물: <파일/코드/문서 — 구체적으로>
제약: <건드리면 안 되는 것, 성능·의존성 조건>
배경: <기존 코드의 어떤 문제 때문에 하는가>
```

채울 게 없는 항목은 빈칸으로 두지 말고 지운다.

### 8. 검증 못 한 것을 끝났다고 하지 않는다

이 프로젝트는 실패가 컴파일 에러가 아니라 **런타임 조용한 실패**로 나온다. 세션 안에서 검증 불가능한 영역:

- `#if UNITY_STANDALONE_WIN && !UNITY_EDITOR` 블록 — 실제 Windows 빌드 없이 확인 불가
- 씬 추가 — Build Settings 등록과 `.unity` 파일명은 코드에서 안 보임
- Win32/DWM 창 제어 실동작

건드렸으면 "수정함"이 아니라 "수정함, 단 X는 실제 빌드로 확인 필요"라고 적는다.

### 9. 효과 수준(effort)은 프롬프트로 못 바꾼다

`effort`는 세션 설정(`/config`)이지 문서나 프롬프트로 올리는 값이 아니다.
"깊이 추론하세요" 같은 문장은 동작을 바꾸지 않는다. 추론이 얕으면 프롬프트를 고치지 말고 effort를 올린다.
