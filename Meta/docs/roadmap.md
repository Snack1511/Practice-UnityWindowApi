# 구조 규약과 마일스톤

> **문서 성격** — `docs/`의 다른 문서가 "지금 어떻게 동작하는가"라면, 이 문서는 **"무엇을 어떤 순서로 어느 계층에 만들 것인가"**다.
> `advise/`(어떻게 바꿔야 하는가)와도 다르다. 계획과 배치 규약을 담는 유일한 문서다.
>
> 두 축을 담는다 — **§1~§2는 시간 축**(어떤 순서로), **§3~§5는 구조 축**(어느 계층에).
> 현황 표시는 대조 시점(2026-09-08) 기준이며, 항목을 구현할 때마다 갱신한다.
> 구조(시스템 · 모듈 · 오브젝트 목록)는 2026-11-24 기획 결정까지 반영했다.

## 1. 3계층 배치 규약

새 기능을 만들기 전에 **어느 계층인지 먼저 정한다.** 계층이 곧 소유자와 수명을 결정한다.

| 계층 | 정의 | 소유자 | 수명 |
|---|---|---|---|
| **시스템** | 프로젝트 전반에 걸쳐 쓰이는 전역 기능 | 메인 컨트롤러 (`MainProcess` → 매니저) | 앱 수명 |
| **모듈** | 특정 컨트롤러가 소유한 개별 기능 | 그 컨트롤러 | 소유자와 함께 |
| **오브젝트** | 각 컨텐츠 안에서 쓰는 객체 | 컨텐츠 | 컨텐츠 진입~이탈 |

판단이 갈릴 때의 기준:

- **여러 컨텐츠가 동시에 필요로 하는가** → 시스템
- **한 컨트롤러만 쓰고, 그 컨트롤러가 사라지면 같이 사라지는가** → 모듈
- **씬/컨텐츠 안에 실제로 배치되어 보이거나 상호작용하는가** → 오브젝트

시스템을 새로 만들면 `MainProcess`의 `Initialize`와 `Release` **양쪽**에 넣는다(해제는 역순).
→ [architecture.md](architecture.md)

### 지금 위치 — 순차가 아니라 병렬 절반

**0~4 중 완전히 닫힌 단계가 하나도 없다.** 전부 절반씩 되어 있다.

```
0 ████████░░  1 █████░░░░░  2 █████░░░░░  3 ████░░░░░░  4 ████░░░░░░  5 ░░  6 ░░
```

단계를 순서대로 닫지 않으면 5단계에서 1~4의 미결이 한꺼번에 터진다.
**각 단계의 "닫힘 판정 기준"을 먼저 정하는 편이 낫다.** 아래 절에 단계별로 정리했다.

### 단계별 닫힘 기준

**기준은 실행이나 명령으로 확인 가능해야 한다.** "잘 동작한다" 같은 문장은 기준이 아니다.
이 프로젝트는 실패가 런타임에야 드러나므로, 판정 방법을 조건과 함께 적는다.

닫힘 조건에 `advise` 항목이 걸려 있으면 그 항목 해소가 곧 조건이다.

### 주의 — 7단계가 1·2를 갈아엎는다

7단계의 "외부 로컬DB 관리, 정석적인 리소스 관리"는 **1·2단계에서 만든 것을 교체한다는 뜻이다.**
지금 구조는 CSV(`TableManager`) + `Resources/`(`ResourcesManager`)인데, 둘 다 7단계에서 바뀔 대상이다.

그래서 1·2단계를 만들 때 **구현이 아니라 경계를 먼저 잡아야 한다.**

- 호출부가 `Resources.Load`나 CSV 파서를 직접 부르지 않게 한다 — 이미 `ResourcesManager` 경유 규약이 있다
- 세이브는 **스키마 버전을 처음부터 넣는다.** 나중에 넣으면 기존 세이브 마이그레이션이 필요해진다 → [advise/003](../advise/003-data-layer.md) 3-5
- Model 계층 설계 시 미리 정해둘 것 → [advise/003](../advise/003-data-layer.md) 3-8

경계 없이 7단계에 도달하면 교체 비용이 호출부 개수만큼 곱해진다.

| 캐릭터 생성 | ❌ **없음** | 코드 0건 (2026-11-24 신설). 유닛 · 용사 · 마을 방어 유닛을 룰로 무작위 생성(직업 · 위치 · 태그 · 스탯, 크기 · 티어는 종족 SO 고정)하고 **태그 40종**의 값을 합친다(고정값 합산 + 성향 % 합연산 보정). 탐색 태그 5종은 유닛 · 용사 효과가 다르다. 상점 · 던전 · 마을이 같이 써서 시스템이다. 고유 유닛 8 · 고유 용사 5 는 고정 데이터 |

**재화 시스템**을 인벤토리와 따로 둔다 (2026-11-06). 재화 정의 · 구매 비용 구조 → `<PLANNING_DOCS>/02.System/시스템_재화.md`.

**세이브는 별도 축이다.** `IOManager`가 있으나 경로가 `Application.dataPath` 기준이라 에디터에서 `Assets/SaveData/`에 파일이 생긴다. → [advise/003](../advise/003-data-layer.md)

## 4. 모듈 — 컨트롤러 소유 기능

| 모듈 | 현황 | 소유 | 비고 |
|---|---|---|---|
| 타임라인 | ❌ 없음 | 던전 · 광산 · 마을 | 던전은 침공 주기(회차마다 빨라지고 이벤트로 느려짐) · 알림 대기(조기 시작 보상 배율). 광산은 채굴 틱 + **오프라인 정산**(기댓값, 상한). 마을은 방어도 시간 감소 · 용병단 재생성. **꺼진 동안 진행은 광산만** |
| RNG | ❌ 없음 | 던전 · 광산 · 마을 · **상점 시스템** | 소유자별 xorshift. 상태를 세이브에 저장 (`정책_RNG_01`). 던전 = 용사 생성 · 탐색 · 조우 · 전투, 상점 = 유닛 생성 (2026-11-24). 광산 흔들림 · 대박, 실패 뒤 파티 저등급 확률, 인장 확률. 마력 아이템 이미지는 연출이라 대상 아님 |
| 보상 | ❌ 없음 | 던전 · 광산 · 마을 | 재화 시스템에 `Give(itemId, n)` |
| 소모 | ❌ 없음 | **상점 시스템** | 재화 시스템에 `Take(itemId, n)`. 구매 비용 = 골드 + 마력 + 영혼 |
| 약탈 시뮬레이션 | ❌ 없음 | 마을 | 부대 vs 단계 방어도. 3단계 연속 돌파, 단계마다 계속/중단. **결과 전에 다음 단계 성공 확률을 계산해 보여줘야 한다.** 용병단은 단발이고 실패해도 남은 체력이 유지된다(판 세이브). 부대 = `부대원` 태그, `부대장` 은 선택, 위치는 진형의 열 (2026-11-24) |
| 방 탐색 | ❌ 없음 | 던전 | 용사 그룹이 유닛 하나처럼 방 타일을 1초에 한 칸 탐색. 함정 발동 · 저항, 조우 → 기습 2회 판정, **열쇠 타일**(찾기 확률 누적, 찾으면 최단 경로). 열쇠에 닿으면 문이 열린다. 한 방에 그룹 하나 — 무작위 이동 · 후퇴는 빈 방만, 텔레포트 방 쌍은 잠금을 공유. 핵의 방은 핵 타일을 찾아 전투 (2026-11-24) |
| 전투 | ❌ 없음 | 던전 | **화면과 분리된 턴제 판정.** 속도 순, 이동 없음, 상대 거리 3단계 사거리, 직업별 타겟. 전멸 또는 제한 시간(생존 수 → 잔여 체력 ÷ DPS), 진 쪽이 물러남. 화면은 결과를 보여주기만 한다. **핵 전투**는 핵이 유닛으로 참전하고 시간 제한이 없다 (2026-11-24) |

**전부 코드 0건이다.** `grep`으로 `inventory` / `reward` / `timeline` / `random` / `economy` 전수 확인 — 일치 없음 (2026-09-08).
인벤토리는 2026-10-29 에 시스템으로 승격돼 이 표에서 빠졌다 → §3.
소모는 2026-11-06 에 소유가 마을에서 **상점 시스템**으로 바뀌었다. 약탈 시뮬레이션은 같은 날 추가됐다.
방 탐색 · 전투는 2026-11-24 에 추가됐다. 던전만 쓰므로 시스템이 아니라 모듈이다 (마을은 약탈 시뮬레이션).

> 모듈은 소유 컨트롤러가 먼저 있어야 붙는다. 소유 관계는 정해졌지만(→ `<PLANNING_DOCS>/03.Content/콘텐츠_역할.md`)
> `ContentBase` 파생 3종(`ContentDungeon` · `ContentVillage` · `ContentMine`)이 **아직 빈 스텁**이다.

## 5. 오브젝트 — 컨텐츠 내 객체

전부 **런타임 생성**이다. 콘텐츠가 켜질 때 만들고 꺼질 때 파괴한다. 씬에 배치하지 않는다 (`정책_오브젝트_01` → `<PLANNING_DOCS>/01.Policy/정책_오브젝트.md`).

> 마을은 시뮬레이션이라 실시간 오브젝트가 없다.

### 재활용 가능한 기존 컴포넌트

전부 전역 네임스페이스의 독립 컴포넌트다. 오브젝트를 만들 때 새로 짜기 전에 확인한다.

| 컴포넌트 | 역할 | 어디에 쓸 만한가 |
|---|---|---|
| `MoveController` | `useRigid` 플래그로 `AddForce` ↔ `Transform.Translate` 전환 | 유닛 · 용사 이동 |
| `SpriteController` | `AddOrGetComponent<SpriteRenderer>` 후 스프라이트 교체 | 유닛 · 함정 · 용사 |
| `FitToCamera` | 오소그래픽 뷰포트 너비에 맞춰 `localScale.x` 조정 | 던전 배경 폭 맞춤 |
| `PlaceToCamera` | 뷰포트 좌표 + 방향 벡터로 화면 가장자리 스냅 | 던전을 화면 가장자리에 붙일 때 |
| `OutboundNotifier` | 등록된 Transform의 화면 이탈을 `LateUpdate`에서 검사 | 용사 진입 · 이탈 감지 |

> 쓰임 열은 2026-11-06 던전 디펜스 기준으로 다시 짚은 **후보**다. 실제로 맞는지는 오브젝트 구현 때 판단한다.

`SpriteController`는 `Resources.Load`를 직접 호출한다(`ResourcesManager` 미경유, TODO 주석 있음). 재사용 전에 정리 대상.
