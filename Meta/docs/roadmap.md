# 구조 규약과 마일스톤

> **문서 성격** — `docs/`의 다른 문서가 "지금 어떻게 동작하는가"라면, 이 문서는 **"무엇을 어떤 순서로 어느 계층에 만들 것인가"**다.
> `advise/`(어떻게 바꿔야 하는가)와도 다르다. 계획과 배치 규약을 담는 유일한 문서다.
>
> 두 축을 담는다 — **§1~§2는 시간 축**(어떤 순서로), **§3~§5는 구조 축**(어느 계층에).
> 현황 표시는 대조 시점(2026-09-08) 기준이며, 항목을 구현할 때마다 갱신한다.

## 1. 3계층 배치 규약

새 기능을 만들기 전에 **어느 계층인지 먼저 정한다.** 계층이 곧 소유자와 수명을 결정한다.

| 계층 | 정의 | 소유자 | 수명 |
|---|---|---|---|
| **시스템** | 프로젝트 전반에 걸쳐 쓰이는 전역 기능 | 메인 컨트롤러 (`MainProcess` → 매니저) | 앱 수명 |
| **모듈** | 특정 컨트롤러가 소유한 개별 기능 | 그 컨트롤러 | 소유자와 함께 |
| **오브젝트** | 각 컨텐츠 안에서 쓰는 객체 | 컨텐츠 | 컨텐츠 진입~이탈 |

판단이 갈릴 때의 기준:

- **여러 컨텐츠가 동시에 필요로 하는가** → 시스템
- **한 컨트롤러만 쓰고, 그 컨트롤러가 사라지면 같이 사라지는가** → 모듈
- **씬/컨텐츠 안에 실제로 배치되어 보이거나 상호작용하는가** → 오브젝트

시스템을 새로 만들면 `MainProcess`의 `Initialize`와 `Release` **양쪽**에 넣는다(해제는 역순).
→ [architecture.md](architecture.md)

§1이 **무엇을 어느 계층에 만드는가**(구조 축)라면, 여기는 **어떤 순서로 만드는가**(시간 축)다.

| 1 | 기본 데이터 로드·저장 구조 설립 | ⚠️ 부분 | 세이브 경로·원자성·스키마 버전 → [advise/003](../advise/003-data-layer.md) 3-1·3-2·3-5 |

| 3 | 기본 UI 구조 + 타이틀 UI·메뉴 UI | ⚠️ 뼈대만 | `UIRoot` 레이어 4개 완성. **타이틀·메뉴 UI 자체는 없다** |

### 지금 위치 — 순차가 아니라 병렬 절반

**0~4 중 완전히 닫힌 단계가 하나도 없다.** 전부 절반씩 되어 있다.

```
0 ████████░░  1 █████░░░░░  2 █████░░░░░  3 ████░░░░░░  4 ████░░░░░░  5 ░░  6 ░░
```

단계를 순서대로 닫지 않으면 5단계에서 1~4의 미결이 한꺼번에 터진다.
**각 단계의 "닫힘 판정 기준"을 먼저 정하는 편이 낫다.** 아래 절에 단계별로 정리했다.

### 단계별 닫힘 기준

**기준은 실행이나 명령으로 확인 가능해야 한다.** "잘 동작한다" 같은 문장은 기준이 아니다.
이 프로젝트는 실패가 런타임에야 드러나므로, 판정 방법을 조건과 함께 적는다.

닫힘 조건에 `advise` 항목이 걸려 있으면 그 항목 해소가 곧 조건이다.

### 주의 — 7단계가 1·2를 갈아엎는다

7단계의 "외부 로컬DB 관리, 정석적인 리소스 관리"는 **1·2단계에서 만든 것을 교체한다는 뜻이다.**
지금 구조는 CSV(`TableManager`) + `Resources/`(`ResourcesManager`)인데, 둘 다 7단계에서 바뀔 대상이다.

그래서 1·2단계를 만들 때 **구현이 아니라 경계를 먼저 잡아야 한다.**

- 호출부가 `Resources.Load`나 CSV 파서를 직접 부르지 않게 한다 — 이미 `ResourcesManager` 경유 규약이 있다
- 세이브는 **스키마 버전을 처음부터 넣는다.** 나중에 넣으면 기존 세이브 마이그레이션이 필요해진다 → [advise/003](../advise/003-data-layer.md) 3-5
- Model 계층 설계 시 미리 정해둘 것 → [advise/003](../advise/003-data-layer.md) 3-8

경계 없이 7단계에 도달하면 교체 비용이 호출부 개수만큼 곱해진다.

### 재활용 가능한 기존 컴포넌트

전부 전역 네임스페이스의 독립 컴포넌트다. 오브젝트를 만들 때 새로 짜기 전에 확인한다.

| 컴포넌트 | 역할 | 어디에 쓸 만한가 |

| `FitToCamera` | 오소그래픽 뷰포트 너비에 맞춰 `localScale.x` 조정 | 스크롤링 배경 |
| `PlaceToCamera` | 뷰포트 좌표 + 방향 벡터로 화면 가장자리 스냅 | 이벤트 오브젝트 |
| `OutboundNotifier` | 등록된 Transform의 화면 이탈을 `LateUpdate`에서 검사 | 스크롤링 배경 재배치, 이동 캐릭터 |

`SpriteController`는 `Resources.Load`를 직접 호출한다(`ResourcesManager` 미경유, TODO 주석 있음). 재사용 전에 정리 대상.

## 7. 미정 — 정해야 진행되는 것

이 문서는 러프한 단계·계층 배치까지만 담는다. 아래는 **결정 전에는 착수해도 뒤집힌다.**
전부 5단계(인게임 컨텐츠) 착수 전에 정해져야 하는 것들이다.

- **컨텐츠 3종의 역할** — `ContentDungeon` · `ContentVillage` · `ContentMine`이 각각 무엇인가. 어느 모듈을 소유하는가
- **배낭이 UI인가 오브젝트인가** — 목록에는 오브젝트로 있으나 격자·슬롯·아이템은 UI 레이어(`Window`/`Popup`)에 놓일 수도 있다. 인벤토리 모듈과의 경계도 함께
- **RNG 재현성 정책** — 시드를 저장하는가. 저장하면 세이브 스키마에 들어간다
- **경제의 단일 자원 vs 복수 자원** — 보상·소모 모듈이 공유할 자원 정의
- **오브젝트를 씬에 배치하는가, 런타임 생성하는가** — UI를 전역 `UIRoot` 밑으로 옮긴 것과 같은 판단이 필요하다
