## A. 구현 명세서

기능 하나의 전체 구조를 담는 **정본** 문서. 커지면 인덱스 문서 + 시스템별 분할.

```markdown
# <기능명> — 구현 명세서 (인덱스 · 개요 · 데이터)

## 문서 구성          # 분할 문서 목록과 각 문서가 다루는 범위
## 최신화 이력         # YYYY-MM-DD — 무엇을 갱신했는지 한 줄씩 누적
## 표기 기준          # 이 문서군에서 쓰는 기호·용어 정의

## 1. 개요
### 1.1 시스템 정의
### 1.2 진입 조건
### 1.3 화면 구성

## 2. 데이터 / 테이블 명세
### 2.N <테이블명> — 컬럼·의미·참조 관계 (핵심 테이블에 ★)
### 2.끝 참조 외부 테이블

## 3. 코드 구조 지도    # 클래스/파일 ↔ 역할 매핑, 로컬 저장 키 목록

## 4. 공통 규약        # 이 기능 작업 시 지켜야 할 것. 함정에 ★함정
### 4.N <규약 주제>    # 데이터 파이프라인, UI 규약, 에셋 편집 주의, 모듈 경계

## 5. 미해소 항목      # 전 시스템 공통으로 남은 문제·결정 대기
```

## B. 이관(포팅) 명세서

브랜치/버전 간 기능 이식 1건의 기록. 이관 규칙은 [05-memory.md](05-memory.md)가 아니라 아래 §이관 규칙 참고.

```markdown
# <기능명> — <소스> → <대상> 이관 명세서

> 작성: YYYY-MM-DD / <세션·워크트리명>
> 소스: `<원본 브랜치>` tip `<SHA>`
> 기획: <링크> / 선행: <선행 커밋·선례 문서>

## 1. 이관 이력        # | 시점 | 커밋 | 내용 | — 1차/롤백/재이관 누적
## 2. 이번 이관에서 달라진 것
### 2-1. 선행 작업과의 정합
### 2-2. 결함 수정      # | # | 파일 | 결함 | 수정 | — 컴파일·검증 기준 전수 기록
### 2-3. 검증 결과      # 무엇을 어떤 방법으로 감사했고 결과가 어땠는지

## 3. 데이터 현황       # 기록만 — 테이블 파일 무수정 원칙
                       # 반입 확인 / 주의(기획 확인 필요) / 부재 로 구분
## 4. 남은 확인 (에디터/QA)   # 번호 목록 — 코드 밖에서 확인해야 할 것
## 5. 관련 문서        # 정본 커밋, 롤업 문서, 방법론 선례
## 6. <대상> 적용 (이관 이후)  # 이식 후 대상 환경 요구에 맞춘 추가 작업
```

## C. 통합 롤업 문서

여러 건의 같은 성격 작업(이관 시리즈 등)을 한 곳에서 추적. **상세는 각 문서가 정본.**

```markdown
# <작업군 이름> — 통합 명세서

> 성격: 항목 누적형 롤업. 상세는 각 폴더 문서가 정본, 여기서는
> **무엇을 언제 어떻게 가져왔고 무엇이 남았는지**만 모은다.

## 0. 공통 규약
### 0-1. 방법론        # 왜 이 방식인가 (예: 왜 cherry-pick이 안 되는가 + 예외 선례)
### 0-2. 커밋 메시지 형식   # Follow/List/Change/Check → 02-git.md §4
### 0-3. 공통 리스크    # 매 건마다 확인할 구조적 위험 목록

## 1. 항목 현황        # | # | 항목 | 대표 커밋 | 상태 | 상세 명세 링크 |
## 2. 항목별 보충      # 표에 못 담는 항목별 특이사항·확정 규약
## 3. 실제로 터진 문제 — 재발 방지 체크리스트
                      # 되돌린 사례별로: 무엇이 / 왜 / 어떻게 재발 방지
```

## D. 작업내역

`YYYY-MM-DD/작업내역_<기능>_<주제요약>.md`. 같은 날 여러 건이면 파일을 나누고 상호 링크.

```markdown
# <기능명> — 작업 내역 (YYYY-MM-DD, <주제>)

<한 문단: 기획서 근거(§ 번호까지) + 무엇을 어떻게 했는지 요약>
대상: `<핵심 파일들>`

## 요구사항            # 이번 작업의 요구 불릿 (기획서 조항 인용)
## 1..N. <진행 내용>   # 확인한 현황 → 판단 → 구현
                      # "수정 불필요" 판정도 근거와 함께 기록한다

## 변경/추가 파일       # 경로 — 무엇을 했는지 한 줄씩
## 후속 / 확인          # 육안 확인 권장 사항, 다음 세션에 넘길 것
```

## E. Change Log

QA 티켓 여러 건을 한 번에 처리한 기록. 티켓별로 **의도 / 원인 / 변경** 3단.

```markdown
# <기능명> — 변경 내역 (Change Log)

- **프로젝트**: <프로젝트명>
- **작업일**: YYYY-MM-DD
- **대상 컨텐츠**: <컨텐츠 식별자>
- **작업자**: <이름>

## N. <티켓번호> — <증상 한 줄>
**의도/목적**: 어떤 문제를 왜 해결하는가
**원인**: 코드 수준의 근본 원인 (조건·수식·초기화 시점까지)
**변경**
- `<파일>.<메서드>` — 무엇을 어떻게 바꿨는지
```

> **의도/목적 칸을 비우지 않는다.** 사용자 설명 뒤에 있는 목표를 추론해 적는다.
> 변경 내용만 남기면 나중에 판단 근거가 사라진다.

## F. 남은작업

중단/인수인계 시점에 잔여 작업을 **의존성 기준으로 그룹화**해 착수 순서를 제시.

```markdown
# <기능명> — 남은 작업 (순차 정리)

> 정리일: YYYY-MM-DD / 작업자: <이름>
> 브랜치: <브랜치> / 기준: <시점>. <전체 상태 한 줄 요약>
> 명세서: <정본 문서 경로>

작업 가능 순서대로 그룹화. **A → B → C** 순 진행 권장.

## A. 단독 가능 (의존성 없음 — 바로 착수)
## B. <타 직군> 선행 후 마무리   # 예: 디자이너 에셋 선행
## C. <외부 팀> 연동             # 예: 서버팀 선행

각 항목: 번호. **제목** — 상태·선행 조건·완료 판정 기준.
해소된 항목은 ~~취소선~~ + (해소, 날짜)로 유지.
```

## 이관 규칙

한 브랜치/버전의 기능을 다른 브랜치로 이관(포팅)할 때.

**이관 대상은 코드와 에셋이다.** 데이터 테이블 파일(CSV, xlsm, `Resources/Tables` 계열)은 이관 단계에서 건드리지 않는다.

- 테이블 파일의 겹침·충돌·불일치를 발견해도 **고치지 말고 기록만** 남긴다 (커밋 Check 섹션, 명세서 §3).
- 테이블 데이터 정합(값 보정, 행 반입, 겹침 해소)은 이관 이후 별도 단계.
- **경계 사례** — 코드가 테이블 값과 어긋날 때 **코드측 정렬은 이관 범위다** (예: enum 값을 이미 반입된 테이블 값에 맞추는 수정). 테이블 파일 자체 수정은 범위 밖.

**Why:** 테이블은 데이터팀/후속 단계의 몫이라 이관 커밋에 섞으면 코드·에셋 이관과 데이터 반입의 책임 경계가 무너진다.

미해결 사항 기록 형식: **어디서 발견했는지**(파일/시트/키) → **무엇이 어긋나는지**(양쪽 값 비교) → **왜 지금 안 고치는지**.

[02-git.md](02-git.md) §1 "티켓 단위로 diff 분리"와 같은 맥락이다 — 이관 커밋에는 이관 범위의 변경만 담고, 범위 밖 발견 사항은 수정 대신 보고로 처리한다.

## 부록. 반복 확인된 운영 원칙

1. **정본 1곳 + 나머지는 델타만** — 같은 정보를 두 문서에 쓰지 않는다. 롤업은 링크와 상태만.
2. **"안 한 것"도 기록** — 검증 안 된 것(Check), 의도적 제외, 기획 확인 대기를 빠뜨리지 않는다.
3. **결함·검증은 전수 표** — 감사 방법(무엇을 어떻게 대조했는지)까지 적어야 재현·신뢰 가능.
4. **되돌린 사례는 체크리스트로 승격** — 실제로 터진 문제를 재발 방지 항목으로 일반화해 공통 규약에 편입.
5. **잔여 작업은 의존성으로 그룹화** — 담당 직군/팀 기준 A/B/C 그룹이 착수 순서를 자연히 결정한다.
6. **판정 근거를 남긴다** — "수정 불필요" 같은 무변경 결론도 확인 경로와 근거를 함께 기록.
