# 규약 관리 파이프라인

**이 문서들 자체를 어떻게 만들고 갱신하는가.**
[00-process.md](00-process.md)가 "코드 작업 하나를 어떻게 하나"라면, 여기는 "규약을 어떻게 쌓아 가나"다.

```
1. 사용자 메모리 갱신 요청
        ↓
2. 메모리 반영
        ↓
3. 메모리 확인
        ↓
4. 1차 통합 · 충돌 지점 정리        ← 프로젝트 → 범용 추출
        ↓
5. Claude\MD 폴더에 추가            ← 보관소 적재
        ↓
6. 2차 통합 · 최종본 갱신           ← 보관소 안에서 병합
        ↓
7. 최종본 점검
        ↓
8. 프로젝트에 사용
```

**한 번에 다 하지 않는다.** 1~3은 작업 중 수시로, 4~8은 규약이 쌓였을 때 별도로 돈다.

---

## 1. 사용자 메모리 갱신 요청

사용자가 **작업 방식**에 대해 지시한 순간이 시작점이다. 코드 요청과 구분한다.

| 신호 | 예 |
|---|---|
| 교정 | "그거 하지 마라", "이런 식으로 해라" |
| 확정 | "이 방식으로 가자", "앞으로 이렇게" |
| 명시 요청 | "기억해둬", "규칙으로 정해" |

**교정도 요청이다.** 사용자가 "기억해"라고 말하지 않아도 작업 방식에 대한 지시면 3단계까지 간다.

## 2. 메모리 반영

**어디에 쓸지 먼저 판단한다.** 두 곳은 성격이 다르다.

| 대상 | 어디에 | 판단 기준 |
|---|---|---|
| 이 프로젝트에만 유효 | 프로젝트 `CLAUDE.md` | 프로젝트 구조·함정에 얽혀 있다 |
| 어느 프로젝트에서든 유효 | 메모리 파일 (`feedback` 타입) | 스택이 바뀌어도 성립한다 |

**둘 다에 쓰지 않는다.** `CLAUDE.md`에 규약을 적었으면 같은 내용을 메모리에 또 넣지 않는다 — 두 벌 관리가 된다.
→ [05-memory.md](05-memory.md)

**이유를 함께 적는다.** 규칙만 남기면 그 규칙 밖에서 어긋난다. `feedback` 타입은 `Why:` / `How to apply:` 필수.

## 3. 메모리 확인

반영 직후 **읽어서 검증한다.** 쓰고 끝내지 않는다.

- 기존 항목과 **중복**되지 않는가 — 있으면 새로 만들지 말고 갱신
- 기존 규약과 **충돌**하지 않는가 — 충돌하면 **덮어쓰지 말고 사용자에게 보고**
- `MEMORY.md` 인덱스에 한 줄이 들어갔는가

여기서 발견한 충돌은 그 자리에서 해결한다. 4단계까지 끌고 가면 원인 추적이 어려워진다.

## 4. 1차 통합 — 프로젝트에서 범용을 뽑는다

프로젝트 규약이 어느 정도 쌓이면 **범용 부분만 분리한다.**

### 뽑는 기준

| 뽑는다 | 남긴다 |
|---|---|
| 언어·엔진이 바뀌어도 성립하는 것 | 특정 API·파일명·폴더 구조에 얽힌 것 |
| 판단 절차, 보고 규칙, 문서 체계 | 이 프로젝트의 함정 목록 |
| git·메모리·모델 운영 | 빌드 명령, 버전 경로 |

고유 내용은 지우지 말고 **`<...>` 플레이스홀더로 치환**하고, 바로 밑에 원본 예시를 인용문으로 남긴다.
채우는 방법이 함께 보여야 다음 프로젝트에서 쓸 수 있다.

### 충돌 지점 정리 — 이 단계의 핵심

**추출본과 기존 보관 문서가 어긋나는 지점을 목록으로 만든다.** 조용히 한쪽을 고르지 않는다.

기록 형식 — **바꾼 쪽이 아니라 이긴 쪽과 근거를 적는다.**

```markdown
| 쟁점 | 결정 | 근거 |
|---|---|---|
| <무엇이 어긋났나> | <어느 쪽으로 정했나> | <어느 문서 어느 절, 왜> |
```

**결정 못 하는 충돌은 "미해결 — 사용자 결정 필요"로 따로 뺀다.** 임의로 정하고 넘어가지 않는다.

## 5. `Claude\MD` 폴더에 추가

보관소(`Desktop/Claude/MD/`)에 적재한다. **이 시점의 산출물은 아직 초안이다** — 기존 문서와 나란히 놓기만 한다.

바로 병합하지 않는 이유: 나란히 두고 봐야 무엇이 겹치는지 보인다.

## 6. 2차 통합 — 보관소 안에서 합친다

보관소 전체를 읽고 **새 폴더에 최종본을 만든다.** 기존 파일을 제자리에서 고치지 않는다 —
원본이 남아 있어야 통합이 틀렸을 때 되돌아갈 수 있다.

### 합치는 기준

| 상황 | 처리 |
|---|---|
| 같은 주제, 내용도 거의 같음 | **하나로 병합** |
| 같은 주제, 내용이 어긋남 | **충돌** — 4단계 형식으로 결정과 근거 기록 |
| 같은 주제로 보이지만 **역할이 다름** | **분리 유지** + 상위 문서에서 언제 무엇을 쓰는지 갈라준다 |
| 한 파일에 여러 주제가 섞여 있음 | **주제별로 분해**해 각 문서로 흩는다 |

세 번째가 실수하기 쉽다. 이름이 비슷하다고 합치면 둘 다 못 쓰게 된다.

### 산출물 구조

- **진입점 `README.md` 하나** — 무엇이 들어있나, 읽는 순서, 적용 방법, **통합하며 내린 결정**, **미해결 항목**
- 프로세스 문서를 번호로 정렬 — 읽는 순서가 곧 작업 순서
- 스택 종속 규칙은 **부록으로 분리** — 다른 스택이면 통째로 지울 수 있게

## 7. 최종본 점검

프로젝트에 넣기 전에 확인한다.

- **원본 항목이 전부 어딘가에 있는가** — 통합하며 조용히 빠진 규칙이 없는지 원본과 대조
- **문서 간 링크가 실제 파일을 가리키는가**
- **같은 내용이 두 문서에 있지 않은가** — 정본 1곳 + 나머지는 링크
- **`README.md`의 결정 표가 실제 본문과 일치하는가**
- **미해결 항목이 `README.md`에 남아 있는가** — 해결한 척 지우지 않는다

## 8. 프로젝트에 사용

1. 최종본을 프로젝트 `process/`로 복사한다.
2. 프로젝트 `CLAUDE.md` 머리에서 **`process/00-process.md`를 링크**한다. 링크가 없으면 읽히지 않는다.
3. 스택이 다르면 부록을 지운다.
4. **기존 프로젝트 규약과 충돌하는 곳을 확인한다.** 이미 그 규칙으로 해 둔 작업(커밋 등)이 있으면 **소급 적용 여부를 사용자에게 묻는다.**

### 프로젝트 `CLAUDE.md`에 남길 것

`process/`로 뺀 것을 `CLAUDE.md`에 중복해 적지 않는다. `CLAUDE.md`에는 **이 프로젝트에서만 참인 것**만 남긴다.

- 프로젝트 소개와 코드 규모
- 코드 작성 규약 (프로젝트 고유)
- **반드시 알아야 할 함정** — 가장 중요
- 검증 명령과 각 단계가 못 보는 범위

`CLAUDE.md`가 길어지면 매 세션 비용이 된다. **고유 정보 밀도가 가장 높은 문서로 유지한다.**

## 이 파이프라인이 막는 실패

| 단계 | 안 하면 |
|---|---|
| 3. 메모리 확인 | 같은 규칙이 표현만 다르게 여러 벌 쌓인다 |
| 4. 충돌 정리 | 어느 쪽이 이겼는지 아무도 모르고, 다음에 반대로 결정한다 |
| 5. 보관소 적재 | 프로젝트가 끝나면 규약도 같이 사라진다 |
| 6. 역할 분리 판단 | 성격이 다른 문서를 합쳐 둘 다 못 쓰게 된다 |
| 7. 원본 대조 | 통합하며 규칙이 조용히 사라진다 |
| 8. 충돌 확인 | 새 규약과 어긋나는 기존 산출물이 그대로 남는다 |
